core 的崩溃线程是 `reactor_3`，信号 SIGABRT。典型成因是 joinable 的 `std::thread` 被析构。
发生在所有 IO 完成之后、spdk app 停止阶段，不影响已完成的数据，但会让任何脚本 exit != 0。
本机没有 gdb，`coredumpctl` 取不到回溯，需要装 gdb 或编一个 Debug 版本定位。

**问题 2 — 跨进程写→读校验 mismatch（间歇，未定位）**

- 第一次：`dev-verify-1789023647` 写完后新进程读，`Read verify failed, data mismatch at offset 0/4096/8192/12288`（4 条，全错）。
- `sample_data` 是固定 `std::string(io_size, 0x55)`，**跨进程比对是有效的**，不是随机种子导致的误报。
- 之后用 `io_type=write_read` 单进程写读同镜像，无 mismatch；再新进程读该镜像（`wr-test-1`），**0 mismatch**。

即同一套流程重跑一遍就对了，属于间歇性问题，需要多轮复现来判断是首轮 PG/epoch 未收敛，还是读路径快照视图的真 bug。
### 9.4 问题 1 根因：sock 传输引入的线程泄漏（已修）

`cm_pool` 是 `4745db08`（A 组，8/18 sock 后端）引入的。它有一个**全局**实例 `g_pool`，
内部 `std::vector<std::thread> _threads`，worker 循环只在 `_running == false` 时退出：

```cpp
void worker() {
    while (true) {
        _cv.wait(lk, [this]() { return !_running || !_q.empty(); });
        if (!_running && _q.empty()) { return; }
        ...
    }
}
```

`pool_impl::stop()` 会把 `_running` 置 false 并 join 所有线程，但**全代码库没有任何地方调用它**
（`grep` 只搜到定义本身）。而 `src/msg/client.cc:31` 的构造函数里调了 `ensure_started()`。
于是任何用过 msg client 的进程，退出时 `g_pool` 析构，成员 `std::vector<std::thread>` 析构时
线程仍是 joinable → `std::terminate()`。

修法（提交 `bc79fbbe`，放在 A 组之后，因为 cm_pool 是 A 组引入的）：

```cpp
class pool_impl {
public:
    ~pool_impl() { stop(); }   // 新增：进程退出时收掉 worker，且幂等
    ...
};
```

选析构而不是在 `client::~client()` 里显式 `stop()`，是因为 g_pool 是全局共享的：
OSD 可能有多个 client 实例，任一实例析构就把池停掉会误伤其他人；析构只在进程退出时跑一次。

### 9.5 问题 2 结论：不复现，判定为集群刚起时的偶发

连跑 5 轮 `run-dev-write-read-verify.sh`，`mismatch` 计数全为 0；此后降级、杀 leader、恢复后的
多轮也全为 0。首轮那次 mismatch 只在集群刚建池的头几分钟出现一次，判定为 PG/epoch 未收敛导致，
不是读路径的确定性 bug。**建议在 PR 1.1 的 signoff 脚本里加“等所有 PG active 再开始写”的前置检查**，
把这类首轮抖动挡在门外。

#### 11.5.1 根因修正（2026-09-10 晚，实验后）

**真正的问题在 `run-raft-dev-regression.sh` 自己**：它的 `load_osd_map()` 不查 mon，
而是从 monitor.log 里抓**最后一条** `ProcessGetOsdMapMessage done` 日志解析端口

1. **脚本用刮日志代替活查询**（主因，`load_osd_map` 的取数方式天然有竞态）；
2. raft_membership 对连接失败**不重拉 map、不超时**，静默卡死（`ff9d32a4` 把重连日志

3. CPU 高是 SPDK reactor poll 模式的正常现象，**不是** bug 证据——修正此前"忙等"的说法；

### 11.5.7 场景 A 根因定位与修复：恢复会话串行化（2026-09-11 下午）

**18 个会话的机制**：osd2（新 leader）同时派发 node 1 和 node 3 两个快照恢复

互相拆台，全部从头再来（431 个分块 ≈ 18 会话 × ~24 块）。leadership 只易主 2 次，不是主因。

**修法（`4a7eceac`）**：恢复会话串行化——占线时把节点挂入 `_recovery_pending` 队列（去重），
会话结束（成功/失败路径）后 `dispatch_pending_recovery()` 补发；被排队的节点**不抑制心跳**，
选举定时器持续被喂。
